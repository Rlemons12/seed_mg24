# Data management protocol phase 1

This phase keeps the direct XIAO MG24 Sense-to-Raspberry Pi BLE architecture. It adds durable delivery semantics without changing provisioning, reset, or lifecycle behavior.

## Sampling and reporting

`sample_interval_ms` controls when the ordinary microphone channel accepts a physical observation. `processing_interval_ms` controls local processing. `report_interval_ms` independently controls when routine telemetry is created. A report includes `sc`, the number of accepted samples since the previous report, and the last processed sample. The separate high-rate vibration FIFO and feature-window pipeline is unchanged.

## Record identity and compatibility

Legacy telemetry schema version 1 remains accepted and receives no persistence ACK. New firmware advertises:

```json
{"data_management":{"telemetry_version":2,"boot_id":true,"persistence_ack":true,"backlog_ack":true,"flash_journal":true,"flash_summary_interval_seconds":60,"flash_summary_capacity":32,"flash_batch_size":4}}
```

Schema version 2 adds `bid`, 16 lowercase hexadecimal characters representing 64 random bits generated by the Bluetooth stack at boot; `s`, an unsigned 32-bit sequence beginning at 1; and optional `sc`, the routine aggregate sample count.

The durable identity of a channel reading is `(device_id, boot_id, sequence, channel)`. The boot identifier is random, does not expose MCU identity, and is never written to NVM. Sequence numbers are RAM-only. Firmware must reboot into a new boot ID before sequence rollover; it must not wrap within one boot session.

## Buffer and persistence ACK

The firmware has a 24-record RAM buffer. Each 292-byte record retains the exact bounded BLE payload, for 7,008 bytes total. Normal records overwrite the oldest equal-priority normal record when full. A lower-priority incoming record cannot displace a higher-priority record.

Firmware 0.1.4 adds a separate restart-safe NVM3 circular journal. It records at most one compact telemetry summary per minute while BLE is disconnected; it never writes every 100 ms live sample. Four summaries are batched into each flash object and eight rotating objects retain 32 committed summaries. This bounds storage, write frequency, RAM use, and replay work. An outage shorter than one batch can remain RAM-only, so up to three staged summaries can be lost on a sensor power failure.

Persistent summaries retain their original boot ID, sequence, device uptime, battery voltage, IMU values, and sample count. They replay oldest-first before the ordinary RAM backlog. A fully acknowledged batch is deleted. Partial acknowledgement advances only in RAM; after a power loss it can replay a duplicate, which SQLite safely deduplicates before acknowledging again.


`TACK 2` acknowledges a sequence safely represented in SQLite for that boot. Receipt, parsing, or queueing is not sufficient. The gateway sends it only after the transaction containing both readings and synchronization state commits. The sensor removes RAM records through that sequence only when the boot ID matches its current boot. A flash-journal acknowledgement instead matches the original boot ID stored in the oldest journal entry, allowing restart-safe replay without reusing telemetry identity.

Journal replay is marked delayed. If the sensor has not rebooted, it includes the elapsed replay age and the gateway reconstructs the approximate measurement time. If the sensor rebooted, no trustworthy wall-clock anchor exists; the reading is retained with an unknown measurement time and is excluded from current battery charge detection.

If an ACK is lost, the oldest record remains buffered and is retransmitted. An exact duplicate is recognized from SQLite and ACKed again. Reuse of the same identity with different content increments the durable conflict counter, preserves the original data, and receives no ACK.

## Gateway synchronization state

`telemetry_sync_states` stores one row per registered device and sensor boot with the first sequence, highest seen sequence, highest contiguous persisted sequence, missing count, duplicate count, conflict count, and update time. This state and the readings are updated in one transaction, so restart recovery does not depend on Python memory.

Gaps above the contiguous frontier remain unacknowledged until the missing sequence arrives. Filling a gap advances the frontier across already persisted later records. A new boot ID creates an independent sequence domain.

## Scope and physical validation

The flash journal stores periodic telemetry summaries, not high-rate vibration windows or every live sample. Physical validation is still required for NVM3 endurance, abrupt power loss during writes, RF-loss ACK recovery, multi-hour outages, replay current draw, and battery-runtime impact.
